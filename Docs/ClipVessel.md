# Clip Vessel
This module serves to clip or truncate a vessel based on user provider points. The user must provide a surface as input (in either model or segmentation format) as well as vessel centerlines created by the VMTK module [**ExtractCenterline**.](https://github.com/vmtk/SlicerExtension-VMTK/blob/master/Docs/ExtractCenterline.md). All branches/vessels should contain a centerline otherwise the clipping may produce undesired geometries in regions without a centerline.  Finally, the user must provide a list of fiducial points that represent where the model will be clipped. The first point is assumed to be the vessel inlet and will clip accordingly. If the output model needs to be capped this can be triggered by the checkbox. The module outputs the clipped surface.

## Capping the clipped ends
*Cap output surface* closes every open boundary of the clipped model, and *cap method* selects the shape of the mesh that closes it. **Off by default**: the usual next step is [CFD Mesh Generator](CfdMeshGenerator.md), which makes the caps itself and puts them where they belong - on the inner surface, past a boundary layer - so capping here only to have them opened again there is a round trip for nothing. Turn it on for a surface that has to leave this module closed. Each method is one of the capping filters of VMTK:

- **Center point** (default) inserts a point at the centre of the hole and fans triangles out from it to the boundary. Flat, and the cheapest, but every triangle meets at one vertex, which makes for a badly shaped element there and a cap that gets no finer as the boundary does.
- **Simple** fills the hole with a single flat polygon, triangulated without adding any points. The cap lies exactly in the plane of the cut and its triangles all sit on the existing boundary vertices, so nothing new is introduced into the mesh - but the triangles are long and thin on an elongated boundary.
- **Smooth** builds the cap out of concentric rings of cells, which gives much better shaped elements than the other two on a large or elongated boundary. Two settings control it. *Cap roundness* sets how far the cap bulges out of the plane of the cut, following the direction the vessel wall was already heading at the rim rather than turning a corner there: at the default of 0 the cap stays in the plane of the cut, like the other two methods, and raising it domes the cap progressively outward, for a model that rounds off instead of being closed with a lid. *Cap rings* sets how many rings of cells the cap is made of (default 8, more gives a finer cap mesh). These are the only two shape settings the underlying VMTK filter has.

All three tag the caps as separate faces for *label mesh faces* in the same way, and all three produce a triangulated, watertight surface whose cells all face outward. Note that a smooth cap with a nonzero roundness moves the surface outside the clip plane, so if the cut position has to be respected exactly - measuring a length up to the cut, or matching a flow extension inlet - leave the roundness at 0 or use one of the flat methods.

## Labeling the faces
Enable *label mesh faces* to have the module tag every triangle of the output surface with an integer face id, stored in a cell array whose name can be set next to the checkbox (`ModelFaceID` by default, the name that SimVascular and its meshing tools read the faces of a model by). The vessel wall - including any flow extensions grown from it - gets id 1, and each cap gets its own id: the cap of the Nth clip point gets id N+1, so the inlet cap is 2, the cap of the second clip point is 3, and so on. If the input surface already carries face labels of its own, those are kept as faces in their own right: they are renumbered onto 1, 2, 3... in ascending order of their original id (a lone pre-existing face at id 10 becomes 1), the vessel wall takes the next id after them, and the caps follow the wall as before - so a pre-existing patch at id 10 gives face 1 for the patch, 2 for the wall and 3 for the first cap. A cell that the input left unlabeled (id 0 or below) counts as wall. If the input labels every cell, so that there is no wall of its own to label, no id is set aside for one and the caps follow the renumbered faces directly. Capping also closes any hole that no clip point accounts for - a defect in the mesh, such as a single missing triangle - and those fills take the id of the face around them rather than becoming faces of their own; put a clip point on one if it should be its own face. Labels on the input survive preprocessing: it rebuilds the mesh and what it leaves of an existing cell array cannot be relied on, so the labels are re-derived from the original surface by position instead. When preprocessing decimates, the module asks for confirmation first, because the face boundaries can then shift by about one cell. Flow extensions are the one case where labels on the input really are discarded: that filter builds its output from scratch and carries no cell data at all. Which id ended up on which cap is reported next to the clipping status once the module has run, and the output model is colored by the face id array automatically, with a legend naming each face, so the faces can be told apart in the 3D view without setting anything up in the Models module. The wall is drawn in neutral grey and each boundary face in its own hue; the legend lists them by name - *Wall*, the label of the clip point whose cut made each cap (*Inlet*, *Outlet 1*, ...), and *Input face N* for a face the input already carried. Turning the checkbox off puts the model back to its plain surface color and hides the legend.

This is what lets a CFD solver be given a different boundary condition per inlet, outlet, and wall, and lets a remesher keep the wall/cap boundaries as sharp feature edges instead of rounding them off. The ids follow the clip points rather than the internal order in which the caps were created, so moving a clip point around does not renumber the faces of an already configured simulation; a clip point that made no cut simply leaves its id unused. The face id is settled before the surface is cut, and written onto the rim of each end as its boundary label (see *Boundary label arrays* below), so the cap of an end and the end itself are the same number everywhere. Face labeling needs the output surface to be capped in order to have caps to label - on an uncapped surface the whole model is labeled as wall.

### Carrying the names downstream
The face ids travel on the output surface, and from there onto a volume mesh made from it, but a face id is a number and a boundary condition is per vessel: somebody still has to say which cap is the azygous vein. The names for that are already here - they are the labels on the clip points - so the module records where to find them again, on the output model node:

- a node reference, *ClipPoints*, to the clip points markups node whose control point labels the names are;
- an attribute `ClipVessel.FaceIdToClipPointID`, which says which control point each cap's face id came from;
- an attribute `ClipVessel.WallFaceID`, the wall's id, which is not in that map because the wall has no clip point.

This is recorded on every run, whether or not the output is capped and whether or not its faces are labelled: a boundary's label already *is* its cap's face id, so which clip point named which face is settled when the boundaries are labelled, before there is a cap or a cell array to work it out from. That matters for the workflow this is for, which leaves capping to CFD Mesh Generator - the caps belong past the boundary layer - and therefore has no faces to label here either. Recorded off the face labeling instead, the names would be present in every run that does not need them and absent from the one that does.

Only the pointer is recorded, not a copy of the labels, so there is no second copy to go stale: renaming a clip point renames its face, with nothing re-clipped. [CFD Mesh Generator](CfdMeshGenerator.md) copies all three onto the volume mesh it makes, and SimVascular Mesh Prep, in the SlicerSimVascular extension, reads them to name the faces of that mesh without anything being typed twice. A node reference and a node attribute both serialize into MRML, so the record comes back with a saved scene.

The map is keyed by control point **ID** rather than by position in the list, and that is deliberate. A cap's face id is `firstCapFaceId + clip point index`, so deleting a clip point shifts every later index down one; keyed by index, each of those vessels' names would move quietly onto the face of the vessel before it, which downstream is a boundary condition on the wrong vessel and nothing further along the chain can catch it. An ID is stable under insertion and reordering, and is never handed out twice, so a deleted clip point's face simply comes out unnamed - which is a thing an operator can see and fix.

## Advanced
Advanced options include preprocessing of the input surface and the addition of flow extensions.
Refer to [here](https://github.com/vmtk/SlicerExtension-VMTK/blob/master/Docs/ExtractCenterline.md#:~:text=Extract%20centerline-,Preprocessing,-The%20module%20requires) for preprocessing options related to the input surface. When creating flow extensions the user can control the extension length ratio, the extension direction, and the transition method. The extension length ratio sets the length of each extension as a multiple of the radius of the vessel end that it is attached to (for example, 2 adds an extension that is twice as long as the radius of that clipped end, default 2). The extension direction selects where the extension grows: along the direction of the centerline at the vessel end, or along the normal of the clipped boundary. The transition method selects how the original outlet is transitioned to the outlet of the extension: ramp fades the original cross-section into the target one along a smooth curve that is flat at both ends, so the extension leaves the clipped boundary and settles into the uniform tube without a crease (default); linear fades them at a constant rate; thin plate spline warps the transition instead, which loses the finer features of a non-circular outlet within the first few layers of the extension. The transition length ratio sets how much of the extension length is used for the transition (0 = the target cross-section is reached immediately at the clipped boundary, 1 = the whole extension, default 0.25). *Transition to circular cross-section* is enabled by default, which makes the target cross-section a circle; disable it to keep the outline of the clipped vessel end along the whole extension instead, so that the area distribution of a non-circular outlet is not altered (note that a strongly concave outline may be hard to cap).

*Vessel names* lists every clip point with the name of the vessel end it marks, in clip point order, and lets each name be edited in place. Selecting a row also selects that clip point in the 3D views, so you can see which end you are naming. It does the same thing as right-clicking a control point and renaming it, as a list you can work down rather than a hunt through a crowded view - which on a case with two dozen vessel ends is most of the work. A cleared cell does not unname a point: the name it had goes back.

It is worth naming here rather than later. A clip point's label is the name its cap carries downstream: [CFD Mesh Generator](CfdMeshGenerator.md) carries the identity of each vessel end onto the volume mesh, and a case setup reads the names off that, so a vessel named here does not have to be named again after meshing - which otherwise means waiting for a mesh, and waiting again for another if the meshing parameters have to change. The names also become the `mesh-surfaces/` file names and the boundary condition names a solver reports its results under, so they are worth choosing rather than accepting: *Inlet* and *Outlet 7* are what the auto-detected defaults give, and `cap_Outlet_7` is not a name to read a pressure under.

*Boundary label arrays* names the two point data arrays that record which clipped end each boundary point belongs to (`BoundaryLabels` and `BoundaryPointOrder` by default, the names the VMTK filters use). The label an end carries is the face id of its cap, so the two arrays and the face id array are one numbering: the rim of the end that comes out as face 3 carries 3, and there is nothing to translate between the point data that says which end a boundary is and the cell data a solver reads its boundary conditions off. They are written into the output surface rather than removed from it, which is what lets each cap keep the same id from one run to the next, lets a flow extension carry the identity of the end it grew from, and lets [CFD Mesh Generator](CfdMeshGenerator.md) name the caps it makes after the same vessel ends. A point that is on no boundary carries -1, which is no face id at all - it says the point is not on a rim, not that it belongs to any particular face. Change the names only if the input surface already carries arrays under them that mean something else, in which case a surface would be taken for a labeled one; whatever they are called here, the same names have to be set in CFD Mesh Generator for it to find them.

The length of an individual flow extension can also be adjusted: click a clip point to select the vessel endpoint, then use the *extension length scale* slider (in the Inputs section, next to the clip plane adjustment buttons) to scale the length of the extension grown from that endpoint relative to the common length set by the extension length ratio. Endpoints left at 1.0x keep the common length.
